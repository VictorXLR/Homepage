Coordinating AI agents in the terminal with ForgeCode

GUI wrappers come and go. A fast terminal, explicit file-ownership boundaries, and a multi-agent harness that respects your shell history get actual software shipped.

Victor Popoola · November 22, 2026 · 8-minute read

In my first post, I argued that home technology should be judged like plumbing: infrastructure comes before gadgets, and anything that adds maintenance without solving a real problem hasn't earned its keep. I hold my software engineering environment to the exact same standard.

Over the last few months—across 401 tracked sessions and nearly a thousand workspace snapshots—I have moved almost all of my AI-assisted engineering out of heavy IDE sidebars and into the terminal using ForgeCode. Instead of treating an LLM like a chat window that pastes snippets into an editor, I run it as a native shell citizen that coordinates specialized sub-agents directly against my filesystem, compiler, and test runners.

Here is a review of the current system I am running, how I coordinate parallel agents without letting them step on each other, and the projects I have built and shipped with this workflow so far.

Scope and evidence. Everything described here reflects my actual local workstation and repository state as of November 22, 2026: ~/.forge/.forge.toml, ~/.zshrc, ~/.forge/.forge.db (401 conversations, 944 filesystem snapshots), and the project checkouts under ~/Developer. Benchmarks and architectural notes come directly from those local builds and test suites.

01 / Reviewing the current system

Before talking about agents, it helps to look at the underlying machine and shell. If the terminal is sluggish or the local runtime is starved for memory, no amount of prompt engineering will make the workflow feel good.

Workstation and local inference (Apple M4 Pro, 48 GB)

My daily driver is a 14-core Apple M4 Pro with 48 GB of unified memory running macOS 27.2. Unified memory is the deciding feature on this machine: 48 GB is enough to keep a quantized diffusion model or a 128k-context local language model warm in GPU memory while compiling Rust, Go, or Swift in the foreground.

Alongside cloud models, I keep two local inference stacks ready on disk: Apple MLX and PyTorch MPS (with mflux in isolated Python 3.14 virtualenvs next to Python 3.12 Torch environments), and Metal-accelerated llama.cpp / LM Studio servers with Flash Attention enabled—including a one-click inkling.command launcher serving Inkling-2-Mini-Q8_0.gguf with its multimodal projector at a 131,072-token context window on port 8782. Package and runtime isolation is handled by uv, pixi, bun, deno, cargo, and zoxide.

Terminal, Zsh integration, and Rex

I run Ghostty configured with unlocked frame rates (window-vsync = false), programming ligatures, copy-on-select, and a 10 MB scrollback buffer. Inside Zsh, ForgeCode isn't just a binary on $PATH; it initializes via eval "$(forge zsh plugin)" and eval "$(forge zsh theme)" right in ~/.zshrc.

That shell integration changes the feedback loop in three ways:

  • Live command traces: The agent prompt automatically receives the recent <command_trace> along with exact exit codes, so when a build or migration fails, the agent already sees what happened without manual copy-pasting.
  • Terminal multiplexing with Rex: Alongside standard tmux splits, the rex CLI and skill let an agent open tabs, arrange panes, run commands across sessions, and inspect terminal output directly.
  • Local MCP bridge: Configured in ~/.forge/.mcp.json to connect local services (such as metapilot-native over localhost HTTP) directly into the agent toolset.

The ForgeCode harness (~/.forge/.forge.toml)

Out of the box, many coding agents choke when they read a large file or hit a transient API rate limit. My .forge.toml is tuned for high concurrency and resilience: subagents = true, verify_todos = true, max_parallel_file_reads = 64, max_read_lines = 2000, and an exponential backoff retry policy covering HTTP status codes 429 through 529.

My default session profile pairs fast OpenRouter inference (z-ai/glm-4.7-flash for low-latency tool dispatch) with automatic context compaction at 100k tokens and a local SQLite conversation store (.forge.db) backed by automatic file snapshots before every mutation.

02 / How I coordinate agents in the terminal

A single agent with full write permissions on a repository eventually turns into a bull in a china shop: it starts refactoring unrelated files while trying to fix a one-line bug. ForgeCode solves this by splitting responsibilities across three specialized agent personas defined in ~/.forge/agents/ and letting the parent session dispatch sub-agents in parallel.

1. Sage / Strictly read-only research & architecture mapping

Tool access: sem_search, search, read, and fetch. Zero write, patch, or shell execution tools.

Role in the loop: When I drop into an unfamiliar repo or need to trace a 19-migration SQL history, I send Sage in first. It maps module relationships, traces data flow, and returns exact filepath:startLine-endLine citations without any risk of mutating the worktree.

2. Muse / Strategic planning & risk analysis

Tool access: Read and search tools plus plan and sage delegation. Cannot modify source files.

Role in the loop: Muse turns ambiguous feature goals into structured Markdown action plans under plans/ with mandatory checkboxes (- [ ]), explicit verification criteria, and alternative trade-offs. An implementation agent can then execute that plan step by step.

3. Forge / Hands-on implementation & parallel sub-agent dispatch

Tool access: Full filesystem mutation (write, patch, multi_patch, remove, undo), shell, todo_write, skills, and the task tool to spawn parallel sub-agents.

Role in the loop: Forge writes the code, runs the compiler and test suites, and coordinates parallel workers when a feature spans multiple independent modules.

The golden rule of multi-agent coordination: Never launch two write-capable agents on the same worktree without partitioning file ownership. Every parallel task prompt I run includes an explicit contract like: "Own ONLY src/worker/index.ts and src/__tests__/worker.test.ts. Preserve uncommitted edits in all other files."

03 / What I have worked on so far

Reviewing the repositories in ~/Developer and the task history in ~/.forge/.forge.db gives a clear picture of what this terminal workflow actually produces across systems networking, mobile apps, local ML inference, and interpretability tooling.

Salvo (territe) / Delay-controlled UDP bulk file transfer in Go

What it is: Classic TCP streams collapse when a long-haul link has both high latency and random packet loss. Built in pure Go with zero third-party dependencies, Salvo pairs a TLS 1.3 control channel (with SHA-256 certificate pinning) and an AES-128-GCM encrypted UDP data channel that paces packets using queuing delay (one-way delay delta) rather than packet loss, repairing gaps via selective NACK bitmaps and zero-copy mmap file I/O.

Measured results: 1.2 Gbit/s encrypted throughput over loopback on a 1.5 GB payload with full SHA-256 verification, and 348–438 Mbit/s through its built-in userspace WAN emulator (salvo impair) across 50–300 ms RTT paths with 1–3% random packet loss—scenarios where a single classic loss-based TCP stream drops below 3 Mbit/s.

Charms (Mine) / Digital wardrobe & social marketplace

What it is: A full-stack React Native (Expo Router), Zustand, PostgreSQL (19+ RLS migrations), and Supabase Edge Functions app for cataloging a personal closet, planning outfits on a calendar, and trading items.

How parallel agents built it: While a read-only agent audited the 2025–2026 SQL migration chain, parallel implementation agents built the security_private.content_admin_roles SQL migration, the typed adminContentService.ts client, transactional psql security tests, and the React Native AdminContentBrowser UI—each owning disjoint files. Separate parallel runs replaced legacy vision classification with a Cloudflare Workers AI (Clef) fashion pipeline, migrated deep links from mine:// to charms://, enforced default-off notification privacy, and codified database deployment rules into a reusable maintain-supabase skill.

Slize / Hand-drawn NYC craft cocktail notebook & shift game

What it is: An interactive cocktail journal and playable NYC neighborhood bartender shift game built with Expo, React Native Reanimated, Rough.js, and a Cloudflare Worker recipe backend.

How agents shaped it: When an early pass drifted toward generic rounded SaaS cards, I used scoped file-ownership tasks to strip out the boilerplate and rebuild the UI around Rough.js vector hachures, Courier typography, paper textures, and a 120Hz physics-driven Cocktail Dial with haptic ticks, alongside an offline bartender shift game (pour.tsx, bartenderGame.ts) and a freestyle home-bar matcher.

Turbo-Term & Flux-UI / Local Apple Silicon image generation

What they are: Two zero-API-cost creative tools built for the M4 Pro's 48 GB unified memory.

How they work: Turbo-Term (z-image-turbo) runs Tongyi-MAI/Z-Image-Turbo and renders images inline inside Ghostty via the Kitty graphics protocol, backed by single-keystroke hotkeys for seed variations, 2x re-renders, and a persistent mlx_worker.py subprocess that keeps quantized mflux weights warm between prompts. Flux-UI pairs a custom tldraw infinite canvas with a local FastAPI + PyTorch MPS backend running 4-step distilled FLUX.2-klein-9B for visual text-to-image and image-to-image node chaining.

Smaller research builds and native utilities

  • vector-state (outmen): Reads an LLM's residual stream using transformer-lens and Sparse Autoencoders (sae-lens) and renders internal activation states as crisp pictogram signage.
  • HRM browser RL & Neural ASM: Recurrent two-timescale actor-critic models (hrm-game) running in Web Workers with TensorFlow.js for Doom, Pac-Man, and Flappy Bird, plus a differentiable CPU-like reference executor (neural_asm.py) and multiscale city ecosystem simulations (ai/stem).
  • oopa: A single-binary Go clone of Magic Todo that serves both a full-screen terminal UI and an embedded local web server, recursively breaking overwhelming tasks into small steps against a local LM Studio model.
  • bitchat-bot: A Swift bot supporting Nostr WebSocket relays, cryptographic event signing, and offline command responders, built by running transport and responder agents in parallel.
  • btcd: A zero-bundler WebAssembly runner with a custom binary LEB128 section inspector and hand-written .wat demos (image-guided Conway's Game of Life, Tetris, Mandelbrot).
  • Tree Hugger, After Party & VoiceInk: Native iOS/macOS Swift apps—from clustering 700,000 NYC street trees via Socrata to a privacy-first social memory log and a custom-patched local build of VoiceInk.

04 / What breaks and how to keep it sane

Coordinating agents in the terminal is a massive multiplier, but it is not magic. When a session goes sideways, it is almost always for one of four reasons—and each has a mechanical fix:

  1. Concurrent migration and lockfile collisions. When two backend agents create a timestamped SQL migration at the same time, they will pick the same sequence number (like 20261008000016). Fix: assign exact migration numbers in the parent prompt and tell sub-agents to run deno test --no-lock so they don't fight over root lockfiles.
  2. Aesthetic drift toward generic templates. Left to their own devices, coding models love turning distinctive interfaces into generic rounded-card dashboards. Fix: reject generic passes immediately, write down the visual invariants (e.g., "Rough.js ink frames, Courier text, paper surfaces only"), and lock the agent to a single screen component at a time.
  3. Environment drift between local runtimes. Cutting-edge ML packages rarely agree on Python versions (mflux wants Python 3.14 and pillow<13; PyTorch/diffusers wants Python 3.12). Fix: document the boundary in an AGENTS.md file at the repo root and bridge the two environments over a clean stdin/stdout JSON worker rather than forcing them into one broken virtualenv.
  4. Silent state corruption on failure. Agents often write happy-path persistence that overwrites saved user state with defaults when hydration fails. Fix: pair every implementation task with a dedicated read-only review agent whose only job is to hunt for race conditions, stale route callbacks, and destructive error handlers.

That is the real takeaway from 400+ sessions on this stack: AI agents work best when you treat them like Unix processes. Give them a fast terminal, narrow responsibilities, explicit file contracts, and a test suite that doesn't lie.
